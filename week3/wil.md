# 3주차 WIL

## 레포지토리 계층의 역할

애플리케이션의 비즈니스 로직(서비스 계층)과 데이터가 저장된 데이터베이스 사이에서  필요한 데이터를 데이터베이스에 접근하여 **CRUD** (Create, Read, Update, Delete) 작업을 수행하는 역할을 한다.

## 레포지토리가 데이터베이스에 접근하려면

애플리케이션 서버는 DB가 이해할 수 있는 SQL을 연결된 커넥션을 통해 DB에 전달한다. DB는 전달된 SQL을 수행하고 그 결과를 응답, 애플리케이션 서버는 그 결과를 활용한다.

데이터베이스는 MySql을 비롯해 종류가 다양하고 각각의 DB마다 내부 통신 방식, 코드가 다르다. 개발자가 모든 DB별 사용 방식, 코드를 알기 힘들기 때문에 JDBC가 등장한다.

## JDBC

JDBC는 자바에서 DB에 접근하기 위한 표준화된 API이다. JDBC가 내부적으로 각 DB에 맞는 드라이버를 통해 실제 SQL을 전달해주기 때문에 개발자가 특정 DB에 종속되지 않고 같은 방식으로 코드를 작성할 수 있게 된다. 그런데 JDBC와 같이 SQL을 직접 다루는 방식에는 여러가지 한계가 존재한다. CRUD를 위해 유사한 SQL 코드를 반복적으로 작성해야하고, 객체 필드가 하나만 바뀌어도 관련 SQL을 일일이 찾아가 수정해야한다. 스프링은 자바 기반의 프레임워크이다.Java는 추상화, 캡슐화, 상속, 다형성 등 자바의 객체 지향적 특징을 잘 활용하려고 하는데 관계형 DB은 데이터를 구조화된 테이블 형태로 저장하는 것이 목표이다. 이렇게 자바 스프링과 관계형 DB가 지향하는 방향이 다르므로 기능, 표현도 다르다. 결과적으로 자바의 객체와 DB의 테이블 간의 매핑이 힘들어지는 패러다임 불일치 문제가 발생한다.

## **ORM(Object-Relational Mapping)의 등장**

이러한 JDBC의 패러다임 불일치 문제를 해결해 주는 게 ORM 기술이다. ORM은 자바 객체와 관계형 DB의 테이블을 자동으로 매핑하여 개발자가 SQL을 직접 작성하지 않고 객체 지향적인 애플리케이션 구현에만 집중할 수 있게 해준다. 객체를 메서드로 조작하기만 해도 ORM이 내부적으로 적절한 SQL을 실행해준다. 반복적인 CRUD SQL을 작성하지 않아도 돼서 개발 생산성이 크게 향상된다.

## JPA의 개념과 동작 방식

**JPA는** 자바 진영의 ORM 기술 표준으로, 자바에서 객체를 DB에 저장하고 관리하기 위한 인터페이스와 기능을 제공하는 API이다. 대표적인 JPA 구현체는 Hibernate가 있다. 개발자가 직접 JDBC를 다루지 않아도 JPA가 내부적으로 JDBC를 사용하여 DB와 통신한다. 

**엔티티 매니저(Entity Manager):** 객체를 데이터베이스와 연결해 주는 창구 역할을 한다. 엔티티 매니저를 사용해 SQL을 직접 작성하지 않고도 엔티티를 DB에 등록`persist`, 조회`find`, 삭제 `remove` , 수정이 가능하다. 엔티티 메니저는 엔티티를 영속성 컨텍스트에 저장한다.

**영속성 컨텍스트(Persistence Context):** JPA가 엔티티를 관리하기 위해 사용하는 가상 공간. 애플리케이션과 DB 사이에서 객체를 보관하는 가상의 DB같은 역할을 한다. 엔티티 매니저를 통해 영속성 컨텍스트에 접근할 수 있다.

엔티티의 생명 주기

- 비영속 : 영속성 컨텍스트와 관련이 없는 상태
- 영속 : 영속성 컨텍스트에 저장된 상태. 엔티티가 영속성 컨텍스트에 의해 관리됨
- 준영속 : 영속성 컨텍스트에 저장되었다가 분리된 상태
- 삭제 : 영속성 컨텍스트에 엔티티가 삭제될거라고 기록한 상태

# 엔티티 CRUD 과정

## 등록

멤버 1을 등록하기 위해 멤버 엔티티를 생성했다고 하자. 이 시점에서 멤버 엔티티 1은 단순히 자바 객체일 뿐이다. 아직 JPA와는 아무런 관련이 없는 비영속 상태이다. 

em.persist(member1)을 호출하면 멤버 엔티티 1이 JPA가 관리하는 영속 상태가 된다. 이 시점에서 JPA는 내부적으로 엔티티를 DB에 저장하기 위한 SQL 쿼리를 만들고 이를 영속성 컨텍스트에 저장한다.

같은 방법으로 멤버 엔티티 2를 영속성 컨텍스트에 저장한다. 트랜잭션이 커밋되면, JPA는  em.flush()를 내부적으로 실행하여 모아둔 쿼리들을 한번에 DB로 보낸다. 이 쿼리들이 성공적으로 실행이 되면 DB에 새 회원 정보가 반영된다.

이렇게 데이베이스에 쿼리를 바로바로 쓰는 것이 아니라 변경사항들을 모아두었다가 트랜잭션이 완료되는 커밋 시점에 한번에 묶어서 DB에 보내는 구조를 `쓰기 지연 (Write-behind)` 이라고 한다. 이를 통해 DB와의 네트워킹 횟수를 줄여 성능을 최적화할 수 있다.

---

## 조회

member1을 찾기 위해 em.find(member1)을 호출한다. 이러면 일단 먼저 영속성 컨텍스트 내부에서 엔티티를 찾아본다.

영속성 컨텍스트에서 엔티티를 찾지 못하면, 직접 DB에서 엔티티를 조회한다. DB에서 받아온 정보를 영속성 컨텍스트에 올리고 조회된 엔티티를 반환한다.

만약 같은 트랜잭션에서 member1을 한번 더 조회를 한다면, 이번에는 이미 영속성 컨텍스트에 등록된 member 엔티티를 반환한다. 

이렇게 한 번 조회한 객체를 영속성 컨텍스트에 보관해 두었다가, 같은 트랜잭션 내에서 재조회 시 DB 접근 없이 캐싱된 객체를 재사용하는 구조를 **`1차 캐시 (First-Level Cache)`라고 한다. SQL만 사용할 때에는 데이터가 같더라도 조회할 때마다 새로운 객체가 만들어지는데, 1차 캐시를 하면 항상 동일한 객체를 보장하여 반환할 수 있다. 이를 `동일성 보장`이라고 한다.**

## 수정

앞서 살펴본 조회와 동일하게 em.find(member1)을 사용해 수정하고 싶은 엔티티를 DB에서 찾아와 영속성 컨텍스트에 올린다.

영속 상태가 된 멤버 엔티티1의 데이터를 수정한다.

수정 작업이 모두 끝나 트랜잭션이 커밋되면 em.flush()가 자동으로 실행된다. 이때 JPA는 영속성 컨텍스트에 등록된 엔티티들을 대상으로 엔티티의 변경 전 상태와 현재 상태를 비교해 수정된 엔티티를 모두 찾아낸다.

변경을 감지하면  `UPDATE` 쿼리를 생성하고 DB에 반영한다.

이렇게 영속성 컨텍스트가 엔티티의 변경 사항을 자동으로 감지하고, 트랜잭션 커밋 시점에 변경 내용을 DB에 반영하는 것을 `변경 감지 (Dirty Checking)` 이라고 한다. 변경 감지는 영속성 컨텍스트가 관리하는 영속 상태의 엔티티에만 적용된다.

## 삭제

em.find()를 통해 삭제하고 싶은 엔티티를 DB에서 찾아와 영속성 컨텍스트에 올린다.

em.remove()를 호출한다. 이때 즉시 delete 쿼리가 실행되지 않는다. JPA는 해당 엔티티를 삭제 대상으로 표시하고 내부적으로 삭제 SQL을 만들어 보관한다. 영속성 컨텍스트는 더이상 이 객체를 관리하지 않는다. 

트랜잭션이 커밋되는 시점에 JPA가 em.flush()를 하면서 DB에 쿼리를 날리며 반영된다.

## JPQL이란?

단순히 PK로 객체 하나를 찾아오는 findById가 아니라 모든 객체를 가져오는 findAll과 같은 복잡한 조회일 경우에는 SQL이 아니라 JPQL을 사용하게 된다. 

JPQL(Java Persistence Query Language)은 JPA에서 사용하는 **객체 지향 쿼리 언어이다.** JPQL의 문법은 SQL과 비슷하지만, SQL은 DB 테이블 기준으로 쿼리를 작성하고, JPQL은 엔티티 객체를 기준으로 쿼리를 작성한다는 점에서 차이가 있다. SQL은 특정 DB에 종속적인 문법이 존재하여 DB를 바꾸면 쿼리 수정이 필요할 수 있지만, JPQL은 특정 DB에 의존하지 않는다. JPQL로 작성하면 JPA가 설정된 DB 방언(Dialect)에 맞춰 적절한 SQL로 자동으로 바꿔주기 때문이다. JPQL은 객체 지향의 장점을 살려 **상속, 다형성, 연관관계**를 쿼리 내에서 그대로 활용할 수 있다는 장점이 있다.
